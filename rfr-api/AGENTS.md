# Правила модуля rfr-api

## Область действия

- Инструкции действуют для всего `rfr-api` и дополняют глобальные правила и корневой `AGENTS.md`. Они не отменяют требований к Git, файлам и согласованию запуска тестов.
- Пиши ответы и документацию на русском языке, текстовые файлы читай и записывай в UTF-8. Сохраняй имена API и идентификаторы.
- Перед изменениями прочитай корневой `README.md`, `rfr-api/README.md`, соответствующий код и вложенные инструкции. При расхождении описания с реализацией исходи из кода и конфигурации; не исправляй несвязанные расхождения в рамках задачи.

## Назначение и архитектура

Модуль предоставляет GraphQL API Rangiffler и работает как OAuth 2.0 Resource Server. Версии Java, Spring Boot, Gradle и зависимостей определяются файлами сборки.

Исходники находятся в `src/main/java/io/student/rangiffler`.

| Пакет или каталог | Назначение |
| --- | --- |
| `controller` | GraphQL query, mutation и разрешение вложенных полей |
| `service/api`, `service/impl` | Контракты сервисов и бизнес-логика |
| `data/entity`, `data/repository`, `data/projection` | JPA, запросы и проекции |
| `config`, `service/cors` | Безопасность, GraphQL, классификация ошибок и CORS |
| `exception` | Доменные ошибки |
| `service/mock`, `src/main/resources/mock` | Статические данные ленты и фотографий |
| `src/main/resources/graphql` | Схема GraphQL |
| `src/main/resources/db/migration/rangiffler-api` | Миграции БД API |

- Контроллер принимает аргументы и контекст пользователя, затем делегирует сервису. Бизнес-правила и транзакции размещай в сервисном слое, запросы к БД — в репозиториях.
- Соблюдай глобальные правила объектов с учётом необходимых конструкций Spring и JPA. Наличие Lombok, изменяемых entity и статических методов в существующем коде не разрешает произвольно расширять исключения.
- Не вводи новые слои, зависимости и несвязанный рефакторинг ради отдельной задачи.

## Контракт GraphQL

- Источник контракта — `src/main/resources/graphql/query.graphqls`. При изменениях согласованно обновляй обработчики, запросы, хуки и типы клиента; учитывай вызовы в `rfr-e2e`.
- Модели `io.student.rangiffler.model` генерируются DGS в `build/generated/sources/dgs-codegen`. Не редактируй и не добавляй сгенерированные файлы в коммиты.
- Настройка `generateJava` находится в `build.gradle`: `UserConnection` и `PhotoConnection` сопоставляются с `Page`, `Date` — с `LocalDate`. Изменяй сопоставления только вместе с соответствующими возвращаемыми типами и контрактом.
- Вложенные поля разрешай через Spring `@SchemaMapping`. Не вызывай методы контроллеров с этой аннотацией вручную для сборки ответа.
- Сохраняй существующий формат Connection, семантику `page`, `size`, `searchQuery` и стабильную сортировку. Проверяй недопустимые значения на границе.
- При обновлении профиля учитывай текущую семантику: пропущенные и `null`-поля input означают отсутствие изменения. Преобразование nullable внешних моделей выполняй на границе, не распространяй `null` в новые внутренние контракты.
- Для привязки JSON используй существующие импорты Jackson 3 `tools.jackson.databind`, а для дат — `java.time`.

## Безопасность и ошибки

- Текущего пользователя определяй по `sub` проверенного JWT, а не по переданному клиентом имени владельца.
- `POST /graphql` разрешён фильтром, но доступ контролируют аннотации методов: query требуют `read`, mutation — `write`. Не убирай проверки ради доступности endpoint.
- Сохраняй проверку подписи, issuer, срока действия и audience access token. Audience задаётся конфигурацией; `id_token` не предназначен для API.
- Claim `authorities` преобразуется в права без дополнительного префикса. Изменения этого контракта согласовывай с `rfr-auth`.
- В мутациях проверяй принадлежность объектов и допустимость действий. Для дружбы учитывай запрет действий с собой, направление заявки и разрешённые переходы состояний.
- Сохраняй одну связь на пару пользователей и существующую обработку конкурентных изменений. Не заменяй ограничения БД одной предварительной проверкой в Java.
- Используй `GraphQlExceptionResolver`: отсутствующий ресурс — `NOT_FOUND`, некорректные данные и действия — `BAD_REQUEST`, непредвиденная ошибка — `INTERNAL_ERROR` без внутренних подробностей.
- HTTP 200 не доказывает успех GraphQL: проверяй `errors` и `extensions.classification`. Не раскрывай SQL, стек исключения и секреты клиенту.

## Данные и ограничения реализации

- Пользователи, страны и дружба работают с БД. Фотографии, лайки, лента и статистика пока используют mock-обработчики; наличие таблиц не означает готовность функциональности.
- Профиль создаётся при первом запросе текущего пользователя; учитывай это при изменении чтения и авторизации.
- Успешная mock-мутация не подтверждает сохранение или удаление. Не выдавай ответ заглушки за реализацию и не добавляй обходы в клиент или тесты вместо устранения причины.
- Изменения схемы БД оформляй новой миграцией Flyway. Не переписывай применённые миграции и не меняй данные соседнего сервиса напрямую.
- Сохраняй транзакционные границы сервисных операций. Для новых запросов проверяй права, пагинацию и влияние загрузки связей.

## Запуск и проверки

- Конфигурация находится в `src/main/resources/application.yml`. Локальные адреса: API `http://localhost:8081`, GraphQL `/graphql`, GraphiQL `/graphiql`. Доступность GraphiQL проверяй по текущей конфигурации безопасности.
- Для запуска нужны БД с миграциями и доступный auth для проверки JWT. Не запускай `localenv.sh` автоматически.
- Команды из корня проекта в PowerShell:

```powershell
.\gradlew.bat :rfr-api:generateJava
.\gradlew.bat :rfr-api:compileJava
.\gradlew.bat :rfr-api:bootRun
```

- Для Bash используй `./gradlew`. Перед тестами согласуй конкретные классы или методы; примеры команд не являются разрешением на запуск.
- Для исправления ошибки следуй глобальному TDD. Успешная компиляция не проверяет HQL в `@Query`: для этого необходим запуск приложения с БД.
- Форматируй изменяемый код средствами IntelliJ IDEA с настройками проекта. Для изменения только документации сборка и тесты обычно не нужны.
- В отчёте разделяй компиляцию, запуск приложения, проверку GraphQL и автотесты. Указывай фактические результаты и ограничения окружения.

- Моки должны остааваться в проекте до явного указания на необходимость их замены на реальные реализации.
