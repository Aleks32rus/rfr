## Назначение и структура проекта

Rangiffler — учебное приложение о путешествиях с фотографиями, странами, профилями и отношениями между пользователями. Полноценная микросервисная реализация является целью проекта; не считай все описанные в задании возможности уже реализованными.

| Каталог | Назначение | Правила модуля |
| --- | --- | --- |
| `rfr-api` | Сервер GraphQL на Spring Boot, JPA, миграции Flyway, заглушки фотографий и ленты | [AGENTS.md](rfr-api/AGENTS.md) |
| `rfr-auth` | Сервер авторизации OAuth2, регистрация, вход и шаблоны Thymeleaf | [AGENTS.md](rfr-auth/AGENTS.md) |
| `rfr-gql-client` | Клиент на React и TypeScript, Vite, Apollo Client и Material UI | [AGENTS.md](rfr-gql-client/AGENTS.md) |
| `rfr-e2e` | UI-тесты регистрации, входа и профиля, проверки JDBC и инфраструктуры на JUnit Jupiter и Playwright Java с Allure | [AGENTS.md](rfr-e2e/AGENTS.md) |
| `gradle` | Gradle Wrapper | Отдельного AGENTS.md нет |

Перед изменениями прочитай корневой `README.md`, README затрагиваемого модуля и соответствующий код. Основное пространство имён Java — `io.student.rangiffler`.

## Технологии и команды

Версии определяются файлами сборки: Java 25, Gradle 9.7.1, Spring Boot 4.1.1. Клиент использует React 19, TypeScript 6 и Vite 8. Для тестов настроены JUnit 6, Playwright Java и Allure. В документации указана MySQL 8.4.

Команды серверной части из корня проекта в PowerShell:

```powershell
.\gradlew.bat build
.\gradlew.bat :rfr-api:generateJava
.\gradlew.bat :rfr-auth:bootRun
.\gradlew.bat :rfr-api:bootRun
.\gradlew.bat runAll --parallel --max-workers=2
.\gradlew.bat :rfr-e2e:test
```

`runAll` запускает auth и API одновременно; флаги `--parallel --max-workers=2` обязательны, поскольку оба `bootRun` работают до остановки. Перед запуском подготовь MySQL через `localenv.sh`. Клиент запускается отдельно.

Команды клиентской части из каталога `rfr-gql-client`:

```powershell
npm ci
npm run dev
npm run lint
npm run build
npm run preview
```

Для Bash используй `./gradlew` вместо `.\gradlew.bat`. Не обновляй зависимости и файлы фиксации версий без необходимости для задачи.

## Локальное окружение

- Авторизация работает на `http://localhost:9001`.
- API работает на `http://localhost:8081`, адрес GraphQL — `/graphql`, GraphiQL — `/graphiql`.
- Клиент работает на `http://localhost:3001` и требует запущенных сервисов авторизации и API.
- Настройки подключения к БД и профили смотри в `rfr-auth/src/main/resources/application.yaml` и `rfr-api/src/main/resources/application.yml`.
- Параметры клиента и адреса перенаправления авторизации должны соответствовать друг другу. Переменные клиента описаны в `rfr-gql-client/README.md`.
- Для подготовки MySQL используй `localenv.sh`: он выполняет `docker compose up -d mysql --wait`.
- Не добавляй секреты, токены и локальные учётные данные в код, документацию или вывод команд.

## Правила изменения кода

- Форматируй создаваемый и изменяемый код штатным Reformat Code IntelliJ IDEA (`Ctrl+Alt+L`) или её командным форматтером с настройками проекта.
- Следуй существующей архитектуре и форматированию затрагиваемого модуля. Сохраняй разделение на контроллеры, сервисы и репозитории.
- Делай изменения в рамках задачи; не включай несвязанный рефакторинг и массовое форматирование.
- Используй имеющиеся компоненты Material UI и существующие механизмы темизации клиента.
- Для поиска используй `rg` и `rg --files`.
- Сначала проверяй фактическую реализацию: часть операций с фотографиями и лентой возвращает статические данные из `rfr-api/src/main/resources/mock`. Успешный ответ заглушки не означает сохранение изменения.
- Spring Boot 4 использует Jackson 3; для классов привязки данных следуй существующим импортам `tools.jackson.databind`.

## GraphQL и данные

- Контракт клиента и сервера находится в `rfr-api/src/main/resources/graphql/query.graphqls`.
- При изменении схемы согласованно обновляй серверные обработчики, запросы, хуки и типы клиента.
- DGS генерирует модели в `rfr-api/build/generated/sources/dgs-codegen`. Не редактируй эти файлы вручную: меняй схему или конфигурацию `generateJava` в `rfr-api/build.gradle`.
- Вложенные поля разрешай через сопоставления схемы Spring. Не вызывай явно методы контроллеров с `@SchemaMapping` для сборки ответа.
- Соблюдай классификацию ошибок: отсутствующий ресурс — `NOT_FOUND`, некорректные данные или действие — `BAD_REQUEST`, непредвиденная ошибка — `INTERNAL_ERROR` без внутренних подробностей.
- Проверяй массив `errors` ответа GraphQL: HTTP 200 сам по себе не подтверждает успех операции. Клиент показывает сообщения для `BAD_REQUEST` и `NOT_FOUND`.
- При мутациях проверяй права текущего пользователя и принадлежность изменяемых объектов.
- Изменения БД оформляй миграциями Flyway в соответствующем модуле. Не переписывай уже применённые миграции ради новой функциональности.

## Проверки

- Не используй явные ожидания и настройки таймаутов с указанием миллисекунд в тестах. Используй автоматические ожидания действий и проверок Playwright.
- Подбирай проверки под изменение. Для клиентского кода используй `npm run lint` и `npm run build`; для серверного — соответствующие задачи Gradle.
- Перед запуском тестов назови конкретные классы или методы и дождись разрешения, если пользователь ещё не разрешил их запуск в текущем диалоге. Примеры команд не являются разрешением на запуск.
- Для исправления ошибки по возможности добавляй тест, воспроизводящий её, и проверяй результат после исправления.
- Успешная сборка не проверяет корректность HQL в `@Query`: запросы проверяются при запуске приложения с БД.
- Для полноценных E2E-проверок могут потребоваться сервисы, база данных и установленные браузеры Playwright. Не представляй стартовую тестовую заготовку как полноценное покрытие приложения.
- В итоговом ответе указывай, что изменено, какие проверки выполнены и что не удалось проверить. При изменении только документации сборку и тесты обычно запускать не требуется.

## Git и локальные файлы

- Перед изменениями проверяй состояние рабочей копии. Не перезаписывай изменения пользователя, не относящиеся к задаче.
- `git push` запрещён, в том числе через обёртки, алиасы и альтернативные способы отправки изменений.
- Удаление файлов и каталогов запрещено: не используй `rm`, `Remove-Item`, `del`, `erase`, `rmdir` и их аналоги. Вместо удаления переименовывай в `.<name>.<timestamp>.bak`, не перезаписывая существующие резервные копии. Не добавляй `.bak` в коммиты.
- Не создавай коммиты, не отправляй изменения и не выполняй разрушительные операции Git без соответствующего указания пользователя.
- Не добавляй сгенерированные модели, каталоги сборки, `node_modules`, результаты тестов и настройки IDE в коммиты.
- Текущий `.gitignore` исключает `AGENTS.md` и `docs/`: это локальные материалы. Не меняй это правило без запроса пользователя.

## Разрешения на управление окружением

- Без дополнительного согласования разрешены запуск, перезапуск и остановка бэкенда (`rfr-auth`, `rfr-api`), фронтенда (`rfr-gql-client`) и БД MySQL из `compose.yaml`. Запуск тестов согласуй по разделу «Проверки».
- Останавливай только процессы, принадлежность которых этому проекту проверена; не завершай все процессы Java, Node.js или Docker по имени. Для фонового запуска через `Start-Process` используй `-WindowStyle Hidden`.
- Остановка БД не должна удалять контейнеры, тома или данные: используй `docker compose stop mysql`, не `down -v`, `rm` или `prune`.
- Эти разрешения не отменяют ограничения песочницы. Правила команд находятся в `.codex/rules/project.rules`; они загружаются после перезапуска Codex при доверенном проекте.
