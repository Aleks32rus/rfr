# Правила модуля rfr-gql-client

## Область действия

- Инструкции действуют для всего `rfr-gql-client` и дополняют глобальные правила и корневой `AGENTS.md`. Они не отменяют требования к Git, файлам и запуску тестов.
- Пиши ответы и документацию на русском языке, используй UTF-8. Сохраняй имена API и существующий язык интерфейса, если пользователь не просил изменить тексты.
- Перед изменениями прочитай корневой `README.md`, `rfr-gql-client/README.md`, затронутые компоненты, хуки и конфигурацию. Не считай описанные в задании функции уже реализованными.

## Стек и структура

Клиент — SPA на React и TypeScript с Vite, Apollo Client, Material UI и React Router. Версии и доступные команды определяются `package.json` и файлом фиксации зависимостей.

| Каталог или файл | Назначение |
| --- | --- |
| `src/api` | Apollo, OAuth, хранение сессии и обработка ошибок GraphQL |
| `src/hooks` | Хуки именованных GraphQL-операций |
| `src/components` | Общие компоненты, формы, карта, лента и таблицы |
| `src/pages` | Страницы и обработка OAuth-переходов |
| `src/context` | Сессия, справочник стран, диалоги и уведомления |
| `src/types` | Типы данных клиента |
| `src/theme.tsx` | Общая тема Material UI |
| `src/components/AppContent` | Маршруты приложения |

- Сохраняй существующие границы: страница собирает сценарий, компонент отображает интерфейс, хук инкапсулирует GraphQL-операцию, `api` отвечает за транспорт и авторизацию.
- Не добавляй новую библиотеку управления состоянием, маршрутизации, форм или компонентов без необходимости и согласования нетривиального решения.
- Следуй существующему TypeScript-коду и React Hooks. Не обходи проверки типов и правила хуков подавлениями ESLint или произвольным `any`.

## Интерфейс

- Используй существующие компоненты Material UI и проекта. Не создавай собственные аналоги готовых select, dialog, snackbar, table, pagination и других компонентов библиотеки.
- Цвета, типографику и общие стили согласовывай с `theme.tsx`. Сохраняй светлую, тёмную и системную темы; не фиксируй цвет, делающий элемент нечитаемым в другой схеме.
- Сохраняй адаптивность страниц, доступные имена, подписи полей и управление с клавиатуры. Не меняй тексты и структуру элементов без причины, связанной с задачей.
- Для асинхронного интерфейса учитывай загрузку, пустое состояние, ошибку и повтор запроса через существующие компоненты, включая `QueryErrorAlert`.
- Не показывай сообщение об успешном сохранении до подтверждённого результата операции. Не подменяй серверное сохранение состоянием формы или кэша.
- Не меняй несвязанные страницы и не включай массовое форматирование. Код форматируй средствами IntelliJ IDEA с настройками проекта.

## GraphQL и состояние

- Контракт находится в `../rfr-api/src/main/resources/graphql/query.graphqls`. При его изменении согласованно обновляй запросы, мутации, типы, хуки и серверные обработчики.
- Используй существующий Apollo Client и хуки из `@apollo/client/react`. Не добавляй второй клиент или прямые запросы в компоненты для обхода общей обработки.
- Сохраняй именованные операции, например `GetUser` и `UpdateUser`: `operationName` используется для диагностики и синхронизации E2E.
- Общие типы размещай в `src/types`, типы конкретной операции — рядом с её реализацией по существующему образцу. Учитывай nullable и необязательные поля схемы.
- HTTP 200 не означает успех: учитывай GraphQL `errors`. Используй `src/api/graphqlError.ts` для безопасного текста; `BAD_REQUEST` и `NOT_FOUND` допускают сообщение сервера, прочие ошибки — общее сообщение.
- При мутациях согласуй обновление нормализованного кэша, `refetchQueries` и зависимые представления. Не добавляй лишние повторные запросы без необходимости.
- При изменениях ленты сохраняй взаимодействие фильтра страны, `withFriends`, пагинации и `fetchMore`. Смена фильтра не должна смешивать страницы разных выборок.
- Дружба влияет на несколько списков людей. Сохраняй согласованное обновление входящих, исходящих заявок, друзей и общего списка.
- Лента, фотографии и лайки пока обслуживаются mock-слоем API. Обновлённая карточка Apollo или snackbar не доказывают сохранение в БД. Не добавляй клиентское постоянное хранение как обход отсутствующей серверной реализации.

## Авторизация и маршруты

- Используй существующие `authClient`, `authUtils`, `PrivateRoute` и контексты. Не дублируй обмен кодов и токенов в страницах, не предназначенных для OAuth.
- Сохраняй Authorization Code + PKCE и передачу `code_verifier` при обмене кода. Клиент публичный; секрет клиента в SPA недопустим.
- В API передаётся только `access_token` через Bearer. `id_token` используется как `id_token_hint` при logout.
- Сохраняй согласованность `/redirect`, `/authorized`, `/logout` с URI, зарегистрированными в auth. Защищённые страницы `/my-travels`, `/people`, `/profile` используют существующий `PrivateRoute`.
- `GetUser` также создаёт профиль API при первом входе. Не заменяй его одной проверкой наличия токена в localStorage.
- Сохраняй различие HTTP 401, ошибок GraphQL авторизации и обычных ошибок данных. Обычная ошибка запроса не должна безусловно сбрасывать сессию.
- При logout сохраняй отзыв access token, очистку Apollo store, завершение сессии auth и локальную очистку. Не обещай немедленную недействительность JWT в API после отзыва.
- Не добавляй refresh token-сценарий без поддержки со стороны auth. Значения TTL проверяй по серверной конфигурации, а не по расходящимся описаниям README.
- Не выводи токены, PKCE verifier и cookies в журналы, уведомления или отчёты. Переменные `VITE_*` попадают в клиентскую сборку и не предназначены для секретов.

## Конфигурация и проверки

- Используй существующие переменные `VITE_AUTH_URL`, `VITE_API_URL`, `VITE_FRONT_HOST`, `VITE_FRONT_URL`, `VITE_CLIENT_ID`. Не дублируй адреса окружений в компонентах.
- Dev-сервер работает на порту 3001; адрес должен соответствовать redirect URI и CORS auth/API. Для полного сценария нужны запущенные auth и API.
- Команды выполняются из `rfr-gql-client`:

```powershell
npm ci
npm run dev
npm run lint
npm run build
npm run preview
```

- Не обновляй зависимости и файл фиксации версий без необходимости. `preview` раздаёт результат сборки и не заменяет её.
- Для изменений клиентского кода выполняй `npm run lint` и `npm run build`. Сборка проверяет TypeScript и Vite, но не доказывает корректность браузерного сценария и серверного сохранения.
- Отдельного скрипта тестов в `package.json` сейчас нет. Не выдумывай команду `npm test`; перед запуском автотестов согласуй конкретные проверки с пользователем.
- Для изменения только документации сборка и тесты обычно не нужны. В итоговом ответе указывай выполненные проверки и то, что осталось непроверенным.
