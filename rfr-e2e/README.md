# UI-тесты

Перед любым обычным запуском тестов глобальный `StandSchemaExtension` проверяет доступность и миграции обеих БД. Поэтому даже тестам без собственного JDBC-кода в таком запуске нужны подготовленные БД auth и API; для отдельного запуска изолированных unit-тестов можно отключить автоподключение расширений параметром JVM `-Djunit.jupiter.extensions.autodetection.enabled=false`.

Тест `RegistrationTest` создаёт уникального пользователя через интерфейс, проверяет сообщение об успешной регистрации, входит с теми же данными и через страницу путешествий открывает профиль для проверки логина. Локаторы, переходы и проверки страниц находятся в Page Object-классах пакета `io.student.rangiffler.page`. Шаги размечены для Allure.

Для запуска нужны MySQL, сервер авторизации на порту 9001, API на порту 8081 и клиент на порту 3001. Подготовка приложения описана в корневом README. Также требуется браузер Chromium для установленной версии Playwright Java.

Запуск из корня проекта в PowerShell:

```powershell
.\gradlew.bat :rfr-e2e:test --tests io.student.rangiffler.test.RegistrationTest
```

Для другого адреса клиента установи переменную окружения `RFR_FRONT_URL`. Класс теста использует `@UsePlaywright`: расширение JUnit передаёт `Page` в тестовый метод, создаёт отдельный контекст для каждого теста и закрывает его после выполнения, в том числе при ошибке. Жизненным циклом браузера и Playwright также управляет расширение. Каждый запуск использует уникальные логин и пароль. `RegistrationTest` использует `UserFixture` в `try-with-resources`: `user()` предоставляет данные без создания пользователя в БД, а `close()` удаляет созданного через UI пользователя и связанные данные из API и auth по уникальному логину, в том числе при падении теста. Очистка auth выполняется даже при ошибке очистки API; ошибки обеих операций сохраняются в результате теста.

HTML-отчёт Gradle: `rfr-e2e/build/reports/tests/test/index.html`.

## Конфигурация и тестовые данные

Адреса компонентов находятся в `config/TestConfig`. Порядок выбора: системное свойство `rfr.<key>` → переменная окружения `RFR_<KEY>` → константа по умолчанию. Точки в ключе заменяются подчёркиваниями для переменной окружения.

| Константа | Системное свойство | Переменная окружения | Значение по умолчанию |
| --- | --- | --- | --- |
| `FRONT_URL` | `rfr.front.url` | `RFR_FRONT_URL` | `http://localhost:3001` |
| `AUTH_URL` | `rfr.auth.url` | `RFR_AUTH_URL` | `http://localhost:9001` |
| `API_URL` | `rfr.api.url` | `RFR_API_URL` | `http://localhost:8081` |

Gradle передаёт свойства с префиксом `rfr.` в JVM тестов. Пример запуска в PowerShell:

```powershell
.\gradlew.bat "-Drfr.front.url=http://localhost:3001" :rfr-e2e:test --tests io.student.rangiffler.test.RegistrationTest
```

`utils/RandomDataUtils` генерирует логин с префиксом `rfr_` и UUID, а также случайный пароль длиной 12 символов без пробелов. Данные соответствуют ограничениям регистрации и создаются заново для каждого запуска теста.

## Пользователь из БД через JUnit Extension

`@User` поддерживает параметры `friends`, `incomeInvitations` и `outcomeInvitations` типа `int` с начальным значением `0`, например `@User(friends = 2, incomeInvitations = 3, outcomeInvitations = 4) TestUser user`. Расширение преобразует аннотацию в `UserRequest`, получает `UserFixture` через `fixture()` и сохраняет её для автоматической очистки. Отрицательные количества запрещены. Метод `UserRequest.fixture()` оборачивает `SingleUserFixture` в `UserWithFriendsFixture` при `friends > 0`, затем в `UserWithIncomeInvitations` при `incomeInvitations > 0`. Первый декоратор создаёт дружбу со статусом `ACCEPTED`, второй — приглашения `PENDING` от дополнительных пользователей к основному. При `outcomeInvitations > 0` внешним декоратором добавляется `UserWithOutcomeInvitationsFixture`: он создаёт приглашённых через `SingleUserFixture` и связи `PENDING` от основного пользователя к приглашённым. При нулевом количестве соответствующий декоратор не добавляется. `UserRequest(User user)` делегирует все счётчики в основной конструктор, поэтому `UserExtension` не меняется при добавлении атрибутов аннотации.

Аннотация параметра `@User` автоматически подключает `UserExtension`. Расширение создаёт пользователя через Spring JDBC и передаёт его в тест как `TestUser`:

```java
@Test
void databaseUserCanSignIn(Page page, @User TestUser user) {
  new LandingPage(page)
      .open()
      .login()
      .fillLoginForm(user.username(), user.password())
      .signIn()
      .profile()
      .shouldHaveUsername(user.username());
}
```

Класс UI-теста должен быть помечен `@UsePlaywright` для получения `Page`. Аннотация `@User` находится в `io.student.rangiffler.junit.annotation`, модель `TestUser` — в `io.student.rangiffler.data`. Модель содержит `id`, `username`, `password` и неизменяемые списки `friends`, `incomeInvitations`, `outcomeInvitations`; `withOutcomeInvitations(...)` возвращает новый снимок с сохранением остальных данных; пароль скрыт в `toString()`.

Для каждого аннотированного параметра создаётся отдельная цепочка фикстур с общим интерфейсом `UserFixture extends AutoCloseable`. Расширение сохраняет fixture в JUnit Store текущего теста и вызывает `create()` для получения `TestUser`. При завершении контекста теста JUnit 6 автоматически вызывает `close()`, в том числе после ошибки теста.

`create()` записывает пользователя с активными флагами аккаунта и права `read` и `write` в одной транзакции auth. Пароль кодируется тем же `DelegatingPasswordEncoder`, что и в auth. Повторный вызов `create()` до закрытия возвращает того же пользователя. Затем `SingleUserFixture` создаёт профиль API с тем же UUID и страной `ru`. Обе БД должны быть доступны, миграции применены, а страна `ru` должна существовать. Этапы auth и API отслеживаются отдельно: при ошибке создания профиля повторная попытка не дублирует запись auth.

`SingleUserFixture.close()` освобождает только успешно созданные этой фикстурой ресурсы. При конфликте логина в auth чужие аккаунт, права и профиль сохраняются; при конфликте профиля API сохраняется чужой профиль, а собственный уже созданный аккаунт удаляется. Для принадлежащего фикстуре профиля сначала отдельно удаляются связи, затем профиль с зависимыми данными; после этого очищается auth. Ошибка одного шага не останавливает остальные, дополнительные ошибки сохраняются как suppressed. Повторное закрытие после успешной очистки ничего не делает.

Для UI-регистрации и ручной подготовки данных используется отдельный `UserReservation` — `ReservedUserFixture`. Его создание явно передаёт владельцу очистки выделенный тесту логин; существующие чужие логины передавать нельзя. В `RegistrationTest` уникальные данные берутся через `fixture.user()`, а аккаунт создаётся через UI. При выходе из `try-with-resources` резервирование очищает данные по логину, включая фактический UUID, выданный внешней регистрацией. `ReservedUserFixtureTest` проверяет очистку аккаунта, прав и профиля при несовпадении предварительного и фактического UUID.

Каждый декоратор владеет фикстурами дополнительных пользователей. Повторный `create()` сохраняет заданное количество связей. При `close()` сначала очищаются дополнительные пользователи, затем вложенная фикстура; ошибка одного участника не останавливает очистку остальных. При частичной ошибке подготовки уже созданные данные остаются под управлением той же цепочки для последующей очистки.

Fixture можно использовать и самостоятельно:

```java
try (UserFixture fixture = new SingleUserFixture()) {
  TestUser user = fixture.create();
  // Действия сценария с user
}
```

База auth должна быть доступна, а её миграции — применены. Настройки читаются через `TestConfig` с тем же приоритетом системных свойств над ENV:

| Системное свойство | Переменная окружения | Назначение |
| --- | --- | --- |
| `rfr.auth.db.url` | `RFR_AUTH_DB_URL` | JDBC URL, по умолчанию локальная БД `rangiffler-auth` на порту 3306 |
| `rfr.auth.db.username` | `RFR_AUTH_DB_USERNAME` | Имя пользователя БД |
| `rfr.auth.db.password` | `RFR_AUTH_DB_PASSWORD` | Пароль пользователя БД |
| `rfr.api.db.url` | `RFR_API_DB_URL` | JDBC URL, по умолчанию локальная БД `rangiffler-api` на порту 3306 |
| `rfr.api.db.username` | `RFR_API_DB_USERNAME` | Имя пользователя БД API |
| `rfr.api.db.password` | `RFR_API_DB_PASSWORD` | Пароль пользователя БД API |

Настройки подключения должны соответствовать обеим работающим БД. `compose.yaml` требует `MYSQL_ROOT_PASSWORD`, но `TestConfig` не читает эту переменную автоматически: передай соответствующие `RFR_AUTH_DB_PASSWORD` и `RFR_API_DB_PASSWORD` через окружение тестов. При изменении адресов или пользователей БД переопредели также соответствующие ключи таблицы.

## Доступ к базам данных

Пакет `data/db` содержит `Databases` с базами `AUTH` и `API`. У каждой базы свой `DataSource` и `JdbcTransactionManager`, использующий этот же источник данных. Подключение создаётся при выполнении запроса; пул соединений не используется.

Статические методы `Jdbc`:

- `client(database)` возвращает Spring `JdbcClient` для выбранной БД.
- `inTransaction(database, action)` выполняет функцию с `JdbcClient` внутри транзакции и возвращает её результат. Ошибка приводит к откату; вложенные вызовы для той же БД присоединяются к текущей транзакции.
- `sql(resource)` читает SQL из classpath в UTF-8; при ошибке загрузки выбрасывает исключение с путём ресурса.

Объекты `data/db` привязаны к конкретному `TestUser` и не изменяют свои поля:

- `AuthAccount` создаёт аккаунт и его права в одной транзакции, удаляет их по уникальному логину и проверяет наличие аккаунта через `exist()`.
- `Authorities` создаёт и удаляет права аккаунта; `exist()` обнаруживает любые оставшиеся строки, а `complete()` проверяет наличие обеих ролей `read` и `write`. Одна оставшаяся роль не считается полной подготовкой и не скрывается проверкой очистки.
- `Profile` создаёт профиль с заданной страной, удаляет профиль с зависимыми фотографиями, лайками, статистикой и связями в одной транзакции, проверяет наличие профиля.
- `Friendships` создаёт связь с заданным статусом, удаляет все связи пользователя либо только выбранный статус и проверяет наличие связей. Подтверждённая дружба симметрична, приглашение `PENDING` сохраняет направление от владельца объекта к переданному пользователю. Методы `count(status)`, `incomeInvitations()` и `outcomeInvitations()` предоставляют счётчики для проверок без JDBC в сценариях.

`AuthAccount` и `Profile` реализуют `StoredData`, а `Authorities` — расширяющий его `RequiredAuthorities` с методами `create()`, `delete()` и `exist()`. `Friendships` реализует `Relationships`. Методы `exist()` каждый раз читают БД; неизменяемость объектов относится к их полям, а не к состоянию БД.

```java
new AuthAccount(user).create();
new Profile(user, "fr").create();
new Friendships(user).create(peer, FriendshipStatus.PENDING);
new Friendships(user).delete();
```

Удаление по логину позволяет использовать эти же объекты для очистки пользователя, зарегистрированного через UI, чей фактический UUID отличается от предварительно сгенерированного. `SingleUserFixture` хранит объекты аккаунта и профиля, а декораторы создают связи через `Friendships`. Порядок очистки задаётся `TearDown`; права очищаются вместе с аккаунтом.

Все SQL-запросы E2E-модуля находятся в `src/test/resources/sql`. Запросы используют именованные параметры; значения передаются через `.param(...)` без подстановки строк. `AuthAccount` и `Authorities` используют эту инфраструктуру для создания аккаунта и прав в одной транзакции.

Проверка подключений к обеим БД и отката транзакции:

```powershell
.\gradlew.bat :rfr-e2e:test --tests io.student.rangiffler.test.JdbcTest
```

Поэтому автотест использует новый контекст браузера, заполняет форму входа и завершает сценарий проверкой логина созданного пользователя.

## Повторное использование очистки

`TearDown` хранит неизменяемую цепочку действий. `with(Runnable)` добавляет отдельное действие, `withEach(Iterable, Consumer)` добавляет действие для каждого элемента коллекции. Оба метода возвращают новую цепочку; исходная цепочка сохраняется. Состав коллекции фиксируется при вызове `withEach`, а действия выполняются только в `close()` и в порядке добавления.

```java
new TearDown()
    .withEach(friends, UserFixture::close)
    .with(origin::close)
    .close();
```

Ошибка действия не останавливает остальные действия. После выполнения цепочки первая `RuntimeException` выбрасывается повторно, остальные ошибки добавляются к ней как suppressed. Один и тот же экземпляр ошибки не добавляется к самому себе. `SingleUserFixture` использует эту цепочку для удаления связей, профиля и auth, а декораторы — для освобождения дополнительных пользователей и вложенной фикстуры. Проверки состояния и сброс состояния после успешной очистки остаются в самих фикстурах.

## E2E-проверка прекондишенов и действий с дружбой

## Проверки UserExtension через EngineTestKit

`UserExtensionTest` запускает отдельные сценарии настоящим движком Jupiter через `EngineTestKit`. Для запуска нужны только MySQL и применённые миграции обеих БД; браузер и сервисы приложения не требуются. Зависимость `junit-platform-testkit` использует версию из существующего JUnit BOM.

Сценарии получают пользователей через `@User` и публикуют через `TestReporter` события с UUID, логином, состоянием аккаунта, профиля и прав, а также количеством друзей и направленных приглашений. Пароли в события не попадают. Внешние тесты читают `reportingEntryPublished()` и после завершения движка проверяют отсутствие участников в обеих БД. Ручной вызов `close()` не используется: проверяется автоматическое закрытие фикстур в JUnit Store.

Проверяются регистрация расширения через аннотацию, передача подготовленного пользователя и обоих видов связей, разные пользователи для разных параметров и повторных вызовов, повторное получение той же фикстуры в `@AfterEach`, очистка после успешного теста, намеренного падения и ошибки разрешения второго параметра. Отдельные сценарии проверяют отказ параметрам без `@User` и с неподдерживаемым типом. Вложенные классы служат входными сценариями для `EngineTestKit`; намеренное падение внутреннего сценария считается ожидаемым результатом внешней проверки.

```powershell
.\gradlew.bat :rfr-e2e:test --tests io.student.rangiffler.test.UserExtensionTest --console=plain --no-parallel
```

## Пул пользователей через StaticUser

`@StaticUser TestUser user` подключает `UsersQueueExtension`, когда создавать пользователей на лету нельзя. В `StaticUserFixture` находится одна статическая потокобезопасная очередь на JVM из трёх демонстрационных пар username/password; они не создаются в БД и не требуют работающего стенда. Для реального входа пары должны соответствовать уже существующим аккаунтам.

Расширение сохраняет фикстуру в отдельном JUnit Store по индексу параметра до вызова `create()`. Фикстура получает пользователя из очереди с таймаутом три секунды; повторный `create()` до закрытия возвращает того же пользователя. При исчерпании пула выдаётся понятная ошибка, прерывание ожидания сохраняется. `close()` возвращает только взятого пользователя, повторное закрытие безопасно; SQL, удаление и изменение данных БД не выполняются. Возврат не восстанавливает изменения, внесённые тестом в аккаунт: такие тесты должны отдельно определять допустимое состояние данных.

`UsersQueueExtensionTest` через `EngineTestKit` проверяет четыре последовательных выполнения на пуле из трёх и возврат после намеренного падения. События фиксируются через `TestReporter` без паролей. `StaticUserFixtureTest` проверяет повторное получение, таймаут, отсутствие лишних возвратов и конкурентную выдачу четырём потокам. Для этих тестов не нужны БД, приложение или браузер.

```powershell
.\gradlew.bat :rfr-e2e:test --tests io.student.rangiffler.test.UsersQueueExtensionTest --tests io.student.rangiffler.test.StaticUserFixtureTest --console=plain --no-parallel
```
## Изоляция мишеней и проверки очистки

Внутренние сценарии `UserExtensionTest` и `UsersQueueExtensionTest` помечены `@ProbeTarget`. Условие `ProbeTargetCondition` по умолчанию отключает их. Внешний тест явно создаёт `ProbeEngine`, делегирующий выполнение Jupiter с отдельным идентификатором `rfr-probes`, и передаёт `rfr.probe.targets.enabled=true` своему запуску `EngineTestKit`. Условие проверяет и идентификатор корневого движка, и параметр: глобального JVM-свойства недостаточно для запуска мишени обычным Launcher. `ProbeEngine` не регистрируется как сервис общего запуска тестов. Отдельные проверки запускают мишень обычным Jupiter без разрешения и с разрешающим параметром; в обоих случаях ожидается пропуск без получения пользователя.

`UsersQueueExtensionTest` после завершения движка дополнительно получает весь пул и сравнивает UUID с тремя исходными пользователями, затем возвращает их через `close()`. `UserExtensionTest` проверяет отсутствие связей всех 26 участников своих сценариев после закрытия Store. `Friendships.exist()` ищет строки и по UUID, и по логину: проверка очистки продолжает работать после удаления профиля API.

Обычные тесты создают собственных пользователей через `@User` или локальную фикстуру; регистрация создаёт пользователя через UI под управлением `ReservedUserFixture`. Демонстрационный общий пул используется только проверками `@StaticUser` и его фикстуры. `UserExtensionTest` обращается только к Jupiter и БД, браузер ему не требуется.

## Allure-отчёт в CI

После E2E-тестов workflow `.github/workflows/ci.yml` формирует HTML командой `./gradlew :rfr-e2e:allureReport --no-daemon` и публикует его в GitHub Pages. В итогах запуска, в задаче «Опубликовать Allure-отчёт», появляется ссылка «Открыть Allure-отчёт». Она ведёт на последний опубликованный отчёт; следующая публикация заменяет предыдущую. Стандартный адрес этого репозитория — `https://aleks32rus.github.io/rfr/`; фактическая ссылка берётся из результата GitHub Pages, поэтому учитывает и собственный домен.

HTML формируется и после падения тестов, если появились файлы `*-result.json`. Публикация отчёта не меняет результат E2E: упавшие тесты продолжают делать задачу CI неуспешной. Если результатов нет или запуск отменён, публикация пропускается. Исходные `allure-results` отдельно сохраняются как скачиваемый артефакт для диагностики.

Однократная настройка репозитория:

1. В `Settings → Pages → Build and deployment` выбрать `Source: GitHub Actions`.
2. В `Settings → Environments → github-pages → Deployment branches and tags` разрешить PR текущего репозитория: при использовании `Selected branches and tags` добавить правило ветки `refs/pull/*/merge`. Ограничение только основной веткой не позволит этому workflow публиковать отчёты PR.
3. Запустить CI для pull request после попадания изменений workflow в его ветку. Для публикации используются стандартный `GITHUB_TOKEN` с `pages: write` и OIDC с `id-token: write`; отдельный токен и ветка с HTML не нужны.

PR из форков формируют HTML и сохраняют исходные результаты, но не публикуют Pages: у их `GITHUB_TOKEN` нет необходимых разрешений записи. Публикации выполняются последовательно. GitHub Pages в этом публичном репозитории открывает отчёт без авторизации.

Локально HTML можно сформировать без повторного запуска тестов:

```powershell
.\gradlew.bat :rfr-e2e:allureReport
```

Готовые файлы находятся в `rfr-e2e/build/reports/allure-report/allureReport`.

## Контракт SuiteExtension

`SuiteExtension` сохраняет отдельный `SuiteRun` в корневом Store до вызова `beforeSuite`. Оба хука, `beforeSuite(ExtensionContext)` и `afterSuite(ExtensionContext)`, получают один и тот же корневой контекст запуска. Синхронизированный `start()` запускает подготовку один раз и повторно передаёт сохранённое исключение остальным обращениям. При закрытии корневого Store вызывается `afterSuite`, включая случай частично выполненной подготовки. `SuiteLifecycle.failure()` сохраняет причину ошибки после `close()`; дополнительная ошибка закрытия добавляется к ошибке подготовки через `suppressed`. Повторный `close()` не повторяет очистку.

`SuiteExtensionTest` проверяет интерфейс как чёрный ящик через `EngineTestKit` и существующий `ProbeEngine`. Пробы переопределяют только `beforeSuite` и `afterSuite`, публикуют события JUnit и владеют небольшим ресурсом с наблюдаемым `close()`. Тесты не вызывают хуки вручную, не читают внутреннее хранилище расширения и не используют общие статические счётчики. БД, браузер и сервисы приложения не нужны.

16 проверок охватывают однократность подготовки и закрытия для нескольких классов и повторов, работу трёх параллельных классов, закрытие после класса без регистрации расширения, ошибки подготовки, тела теста и закрытия, сохранение обеих ошибок при одновременном отказе хуков, независимое закрытие двух реализаций в обоих порядках регистрации и изоляцию отдельных запусков движка. Контракт требует закрытия даже после частично выполненного `beforeSuite`; ошибка подготовки не должна повторять инициализацию при переходе к другому классу.

Параллельные пробы синхронизируются барьером с ограничением ожидания в пять секунд; внешний тест ограничен тридцатью секундами. Во внутренних запусках автоподключение глобальных расширений отключено. `@ProbeTarget` запрещает обычному Jupiter выполнять намеренно падающие мишени; отдельные проверки подтверждают эту изоляцию.

`SuiteRunTest` отдельно проверяет сохранение исходного исключения после закрытия, добавление ошибки очистки в `suppressed`, защиту от самоподавления, сохранение типа `Error` и однократность повторных вызовов. Используется настоящий контекст Jupiter и локальное расширение с заданными результатами хуков.

```powershell
.\gradlew.bat :rfr-e2e:test --tests io.student.rangiffler.test.SuiteExtensionTest --tests io.student.rangiffler.test.SuiteRunTest --console=plain --no-parallel
```

Падение внешней проверки означает нарушение указанного контракта либо неисправность пробы, которую нужно установить по журналу событий. Намеренные ошибки внутренних мишеней сами по себе ожидаемы; изменение реализации `SuiteExtension` не входит в задачу этих тестов.

## Проверка схемы стенда перед тестами

`StandSchemaExtension` глобально зарегистрирован через `ServiceLoader` и до выполнения тестов проверяет миграции auth и API. Подключения берутся из существующих `Databases` и настроек `TestConfig`; в собственные сообщения расширение не подставляет JDBC URL или учётные данные. Обе схемы проверяются даже при ошибке одной из них, а сообщения об ошибках содержат название схемы, версию миграции, причину и действие для восстановления совместимости.

Задача `processTestResources` берёт SQL непосредственно из `rfr-auth/src/main/resources/db/migration` и `rfr-api/src/main/resources/db/migration`. Ручных копий миграций в тестовом модуле нет. После переключения ветки выполните сборку ресурсов Gradle перед запуском из IDE, чтобы её classpath соответствовал текущим файлам.

`MigrationSchema` вызывает только штатный `Flyway.validateWithResult()`, проверяя версии, контрольные суммы, описания, типы и неприменённые миграции. Игнорирование будущих миграций отключено: применённая миграция, которой уже нет в ветке, тоже останавливает тесты. Пустой набор ресурсов считается ошибкой подготовки проверки. Создание схем и выполнение SQL callbacks отключены; проверка не вызывает `migrate`, `repair`, `baseline` или `clean`.

Если миграции текущей ветки ещё не применены, сообщение предлагает запустить соответствующий бэкенд и дождаться успешного выполнения Flyway. Для лишних или изменённых применённых миграций предлагается вернуть совместимую ветку или исходный файл либо восстановить совместимую локальную БД. Автоматического изменения схемы или исправления истории нет.

`MigrationSchemaTest` проверяет диагностику по результатам Flyway, а `StandSchemaExtensionTest` — вызов обеих схем и сохранение всех причин отказа. Эти проверки используют подставные результаты и не подтверждают доступность реального MySQL. Для их отдельного запуска без БД отключите автоподключение только в JVM этого запуска, например через `JAVA_TOOL_OPTIONS=-Djunit.jupiter.extensions.autodetection.enabled=false`, и выберите два класса через `--tests`.
