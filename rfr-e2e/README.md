# UI-тесты

Тест `RegistrationTest` создаёт уникального пользователя через интерфейс, проверяет сообщение об успешной регистрации, входит с теми же данными и через страницу путешествий открывает профиль для проверки логина. Локаторы, переходы и проверки страниц находятся в Page Object-классах пакета `io.student.rangiffler.page`. Шаги размечены для Allure.

Для запуска нужны MySQL, сервер авторизации на порту 9001, API на порту 8081 и клиент на порту 3001. Подготовка приложения описана в корневом README. Также требуется браузер Chromium для установленной версии Playwright Java.

Запуск из корня проекта в PowerShell:

```powershell
.\gradlew.bat :rfr-e2e:test --tests io.student.rangiffler.test.RegistrationTest
```

Для другого адреса клиента установи переменную окружения `RFR_FRONT_URL`. Класс теста использует `@UsePlaywright`: расширение JUnit передаёт `Page` в тестовый метод, создаёт отдельный контекст для каждого теста и закрывает его после выполнения, в том числе при ошибке. Жизненным циклом браузера и Playwright также управляет расширение. Каждый запуск использует уникальные логин и пароль. `RegistrationTest` использует `UserFixture` в `try-with-resources`: `user()` предоставляет данные без создания пользователя в БД, а `close()` удаляет созданного через UI пользователя и связанные данные из API и auth по уникальному логину, в том числе при падении теста. Очистка auth выполняется даже при ошибке очистки API; ошибки обеих операций сохраняются в результате теста.

HTML-отчёт Gradle: `rfr-e2e/build/reports/tests/test/index.html`.

## Конфигурация и тестовые данные

Адреса компонентов находятся в `config/TestConfig`. Порядок выбора: системное свойство `rfr.<key>` → переменная окружения `RFR_<KEY>` → константа по умолчанию. Точки в ключе заменяются подчёркиваниями для переменной окружения.

| Константа | Системное свойство | Переменная окружения | Значение по умолчанию |
| --- | --- | --- | --- |
| `FRONT_URL` | `rfr.front.url` | `RFR_FRONT_URL` | `http://localhost:3001` |
| `AUTH_URL` | `rfr.auth.url` | `RFR_AUTH_URL` | `http://localhost:9001` |
| `API_URL` | `rfr.api.url` | `RFR_API_URL` | `http://localhost:8081` |

Gradle передаёт свойства с префиксом `rfr.` в JVM тестов. Пример запуска в PowerShell:

```powershell
.\gradlew.bat "-Drfr.front.url=http://localhost:3001" :rfr-e2e:test --tests io.student.rangiffler.test.RegistrationTest
```

`utils/RandomDataUtils` генерирует логин с префиксом `rfr_` и UUID, а также случайный пароль длиной 12 символов без пробелов. Данные соответствуют ограничениям регистрации и создаются заново для каждого запуска теста.

## Пользователь из БД через JUnit Extension

`@User` поддерживает параметры `friends` и `incomeInvitations` типа `int` с начальным значением `0`, например `@User(friends = 2, incomeInvitations = 3) TestUser user`. Расширение преобразует аннотацию в `UserRequest`, получает `UserFixture` через `fixture()` и сохраняет её для автоматической очистки. Отрицательные количества запрещены. Метод `UserRequest.fixture()` оборачивает `SingleUserFixture` в `UserWithFriendsFixture` при `friends > 0`, затем в `UserWithIncomeInvitations` при `incomeInvitations > 0`. Первый декоратор создаёт дружбу со статусом `ACCEPTED`, второй — приглашения `PENDING` от дополнительных пользователей к основному. При нулевом количестве соответствующий декоратор не добавляется.

Аннотация параметра `@User` автоматически подключает `UserExtension`. Расширение создаёт пользователя через Spring JDBC и передаёт его в тест как `TestUser`:

```java
@Test
void databaseUserCanSignIn(Page page, @User TestUser user) {
  new LandingPage(page)
      .open()
      .login()
      .fillLoginForm(user.username(), user.password())
      .signIn()
      .profile()
      .shouldHaveUsername(user.username());
}
```

Класс UI-теста должен быть помечен `@UsePlaywright` для получения `Page`. Аннотация `@User` находится в `io.student.rangiffler.junit.annotation`, модель `TestUser` — в `io.student.rangiffler.data`. Модель содержит `id`, `username`, `password`; пароль скрыт в `toString()`.

Для каждого аннотированного параметра создаётся отдельная цепочка фикстур с общим интерфейсом `UserFixture extends AutoCloseable`. Расширение сохраняет fixture в JUnit Store текущего теста и вызывает `create()` для получения `TestUser`. При завершении контекста теста JUnit 6 автоматически вызывает `close()`, в том числе после ошибки теста.

`create()` записывает пользователя с активными флагами аккаунта и права `read` и `write` в одной транзакции auth. Пароль кодируется тем же `DelegatingPasswordEncoder`, что и в auth. Повторный вызов `create()` до закрытия возвращает того же пользователя. Затем `SingleUserFixture` создаёт профиль API с тем же UUID и страной `ru`. Обе БД должны быть доступны, миграции применены, а страна `ru` должна существовать. Этапы auth и API отслеживаются отдельно: при ошибке создания профиля повторная попытка не дублирует запись auth.

`SingleUserFixture.close()` сначала отдельно удаляет все дружеские связи и входящие и исходящие приглашения пользователя, затем удаляет профиль API с фотографиями, лайками и статистикой, после этого — права и пользователя auth. Отдельное удаление связей сохраняется даже при откате последующей транзакции удаления профиля. Ошибка любого шага не останавливает остальные попытки очистки. Очистка каждой БД выполняется в своей транзакции; общей транзакции между базами нет. Если очистка API завершилась ошибкой, fixture всё равно пытается очистить auth. Ошибки очистки не скрываются, дополнительные ошибки добавляются как suppressed. Повторный вызов после успешной очистки ничего не делает. В `RegistrationTest` данные берутся через `fixture.user()`, пользователь создаётся через UI и удаляется по логину из обеих БД при выходе из `try-with-resources`. Очистка не зависит от вызова `create()` и безопасна, если регистрация не состоялась.

Каждый декоратор владеет фикстурами дополнительных пользователей. Повторный `create()` сохраняет заданное количество связей. При `close()` сначала очищаются дополнительные пользователи, затем вложенная фикстура; ошибка одного участника не останавливает очистку остальных. При частичной ошибке подготовки уже созданные данные остаются под управлением той же цепочки для последующей очистки.

Fixture можно использовать и самостоятельно:

```java
try (UserFixture fixture = new SingleUserFixture()) {
  TestUser user = fixture.create();
  // Действия сценария с user
}
```

База auth должна быть доступна, а её миграции — применены. Настройки читаются через `TestConfig` с тем же приоритетом системных свойств над ENV:

| Системное свойство | Переменная окружения | Назначение |
| --- | --- | --- |
| `rfr.auth.db.url` | `RFR_AUTH_DB_URL` | JDBC URL, по умолчанию локальная БД `rangiffler-auth` на порту 3306 |
| `rfr.auth.db.username` | `RFR_AUTH_DB_USERNAME` | Имя пользователя БД |
| `rfr.auth.db.password` | `RFR_AUTH_DB_PASSWORD` | Пароль пользователя БД |
| `rfr.api.db.url` | `RFR_API_DB_URL` | JDBC URL, по умолчанию локальная БД `rangiffler-api` на порту 3306 |
| `rfr.api.db.username` | `RFR_API_DB_USERNAME` | Имя пользователя БД API |
| `rfr.api.db.password` | `RFR_API_DB_PASSWORD` | Пароль пользователя БД API |

Настройки подключения должны соответствовать обеим работающим БД. `compose.yaml` требует `MYSQL_ROOT_PASSWORD`, но `TestConfig` не читает эту переменную автоматически: передай соответствующие `RFR_AUTH_DB_PASSWORD` и `RFR_API_DB_PASSWORD` через окружение тестов. При изменении адресов или пользователей БД переопредели также соответствующие ключи таблицы.

Запуск проверки расширения через авторизацию в UI:

```powershell
.\gradlew.bat :rfr-e2e:test --tests io.student.rangiffler.test.LoginTest
```

## Доступ к базам данных

Пакет `data/db` содержит `Databases` с базами `AUTH` и `API`. У каждой базы свой `DataSource` и `JdbcTransactionManager`, использующий этот же источник данных. Подключение создаётся при выполнении запроса; пул соединений не используется.

Статические методы `Jdbc`:

- `client(database)` возвращает Spring `JdbcClient` для выбранной БД.
- `inTransaction(database, action)` выполняет функцию с `JdbcClient` внутри транзакции и возвращает её результат. Ошибка приводит к откату; вложенные вызовы для той же БД присоединяются к текущей транзакции.
- `sql(resource)` читает SQL из classpath в UTF-8; при ошибке загрузки выбрасывает исключение с путём ресурса.

Объекты `data/db` привязаны к конкретному `TestUser` и не изменяют свои поля:

- `AuthAccount` создаёт аккаунт и его права в одной транзакции, удаляет их по уникальному логину и проверяет наличие аккаунта через `exist()`.
- `Authorities` создаёт и удаляет права аккаунта; `exist()` требует наличия обеих ролей `read` и `write`.
- `Profile` создаёт профиль с заданной страной, удаляет профиль с зависимыми фотографиями, лайками, статистикой и связями в одной транзакции, проверяет наличие профиля.
- `Friendships` создаёт связь с заданным статусом, удаляет все связи пользователя либо только выбранный статус и проверяет наличие связей. Подтверждённая дружба симметрична, приглашение `PENDING` сохраняет направление от владельца объекта к переданному пользователю. Методы `count(status)`, `incomeInvitations()` и `outcomeInvitations()` предоставляют счётчики для проверок без JDBC в сценариях.

`AuthAccount`, `Authorities` и `Profile` реализуют `StoredData` с методами `create()`, `delete()` и `exist()`. `Friendships` реализует `Relationships`. Методы `exist()` каждый раз читают БД; неизменяемость объектов относится к их полям, а не к состоянию БД.

```java
new AuthAccount(user).create();
new Profile(user, "fr").create();
new Friendships(user).create(peer, FriendshipStatus.PENDING);
new Friendships(user).delete();
```

Удаление по логину позволяет использовать эти же объекты для очистки пользователя, зарегистрированного через UI, чей фактический UUID отличается от предварительно сгенерированного. `SingleUserFixture` хранит объекты аккаунта и профиля, а декораторы создают связи через `Friendships`. Порядок очистки задаётся `TearDown`; права очищаются вместе с аккаунтом.

Все SQL-запросы E2E-модуля находятся в `src/test/resources/sql`. Запросы используют именованные параметры; значения передаются через `.param(...)` без подстановки строк. `AuthAccount` и `Authorities` используют эту инфраструктуру для создания аккаунта и прав в одной транзакции.

Проверка подключений к обеим БД и отката транзакции:

```powershell
.\gradlew.bat :rfr-e2e:test --tests io.student.rangiffler.test.JdbcTest
```

## Проверка сценария через Playwright MCP

Сценарий и локаторы проверены в работающем приложении через Playwright MCP: ссылка `Register`, форма регистрации, сообщение `Congratulations! You've registered!`, переход `Sign in` → `Login`, форма входа, карта и профиль. Для имени пользователя используется роль `textbox` с точным именем `Username`; для паролей — уникальные подсказки полей. Ссылка `Profile` ограничена областью `banner`, поскольку в меню есть вторая ссылка с тем же именем.

При исследовании обнаружена сохранённая сессия сервера авторизации: кнопка `Login` могла сразу открыть кабинет другого пользователя. После выхода через интерфейс выполнен вход с данными нового аккаунта; в профиле подтверждён его логин. Поэтому автотест использует новый контекст браузера, заполняет форму входа и завершает сценарий проверкой логина созданного пользователя.

## Повторное использование очистки

`TearDown` хранит неизменяемую цепочку действий. `with(Runnable)` добавляет отдельное действие, `withEach(Iterable, Consumer)` добавляет действие для каждого элемента коллекции. Оба метода возвращают новую цепочку; исходная цепочка сохраняется. Состав коллекции фиксируется при вызове `withEach`, а действия выполняются только в `close()` и в порядке добавления.

```java
new TearDown()
    .withEach(friends, UserFixture::close)
    .with(origin::close)
    .close();
```

Ошибка действия не останавливает остальные действия. После выполнения цепочки первая `RuntimeException` выбрасывается повторно, остальные ошибки добавляются к ней как suppressed. Один и тот же экземпляр ошибки не добавляется к самому себе. `SingleUserFixture` использует эту цепочку для удаления связей, профиля и auth, а оба декоратора — для освобождения дополнительных пользователей и вложенной фикстуры. Проверки состояния и сброс состояния после успешной очистки остаются в самих фикстурах.

## Проверки UserExtension через EngineTestKit

`UserExtensionTest` запускает отдельные сценарии настоящим движком Jupiter через `EngineTestKit`. Для запуска нужны только MySQL и применённые миграции обеих БД; браузер и сервисы приложения не требуются. Зависимость `junit-platform-testkit` использует версию из существующего JUnit BOM.

Сценарии получают пользователей через `@User` и публикуют через `TestReporter` события с UUID, логином, состоянием аккаунта, профиля и прав, а также количеством друзей и направленных приглашений. Пароли в события не попадают. Внешние тесты читают `reportingEntryPublished()` и после завершения движка проверяют отсутствие участников в обеих БД. Ручной вызов `close()` не используется: проверяется автоматическое закрытие фикстур в JUnit Store.

Проверяются регистрация расширения через аннотацию, передача подготовленного пользователя и обоих видов связей, разные пользователи для разных параметров и повторных вызовов, повторное получение той же фикстуры в `@AfterEach`, очистка после успешного теста, намеренного падения и ошибки разрешения второго параметра. Отдельные сценарии проверяют отказ параметрам без `@User` и с неподдерживаемым типом. Вложенные классы служат входными сценариями для `EngineTestKit`; намеренное падение внутреннего сценария считается ожидаемым результатом внешней проверки.

```powershell
.\gradlew.bat :rfr-e2e:test --tests io.student.rangiffler.test.UserExtensionTest --console=plain --no-parallel
```
