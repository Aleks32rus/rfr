# Правила модуля rfr-e2e

## Область действия и приоритет

- Инструкции действуют для всего `rfr-e2e` и дополняют глобальные правила и корневой `AGENTS.md`.
- Пиши ответы, документацию и описания шагов на русском языке. Сохраняй имена API, идентификаторы и фактический текст интерфейса. Читай и записывай текст в UTF-8.
- При конфликте соблюдай порядок из глобальных правил: прямое указание пользователя, безопасность Git/Files, существующая архитектура, затем более конкретное правило. Этот файл и скилл не дают самостоятельного разрешения нарушать более приоритетные требования.
- Перед изменениями прочитай корневой `README.md`, `rfr-e2e/README.md`, соответствующий код и вложенные `AGENTS.md`, если они появятся. Для Page Object используй `.agents/skills/rfr-page-objects/SKILL.md`.
- Документация описывает также планы проекта. Проверяй фактическую реализацию; существующие отступления от правил не являются образцом для нового кода. Не исправляй их вне задачи.

## Назначение и структура

Модуль содержит UI-тесты, проверки тестовой инфраструктуры и средства подготовки данных. Используются Java, JUnit Jupiter, Playwright Java, Allure и Spring JDBC. Версии и зависимости проверяй в файлах Gradle; не обновляй их без необходимости.

Базовое пространство имён — `io.student.rangiffler`, исходники находятся в `src/test/java`.

| Пакет или каталог | Назначение |
| --- | --- |
| `test` | Сценарии и проверки поведения |
| `page` | Page Object отдельных страниц |
| `page/component` | Переиспользуемые части интерфейса |
| `config` | Конфигурация окружения через `TestConfig` |
| `data`, `data/db` | Модели данных, репозитории и JDBC-инфраструктура |
| `fixture` | Подготовка данных и управление их жизненным циклом |
| `junit/annotation`, `junit/extension` | Аннотации и расширения JUnit |
| `utils` | Существующие средства генерации данных; не основание создавать новые utility-классы вопреки глобальным правилам |
| `src/test/resources/sql` | SQL с именованными параметрами |
| `src/test/resources/images` | Изображения для сценариев |

## Окружение и конфигурация

- Для UI-сценариев нужны MySQL с применёнными миграциями, auth, API, клиент и Chromium для установленной версии Playwright.
- Используй `TestConfig`: приоритет — системное свойство `rfr.<key>`, затем переменная `RFR_<KEY>`, затем значение по умолчанию. Точки в ключе заменяются подчёркиваниями для ENV.
- Адреса по умолчанию: клиент `http://localhost:3001`, auth `http://localhost:9001`, API `http://localhost:8081`. В коде сценариев и PO не дублируй адреса; используй `FRONT_URL`, `AUTH_URL`, `API_URL`.
- Настройки БД передавай через существующие ключи `rfr.auth.db.*` и `rfr.api.db.*` или соответствующие ENV. Не добавляй секреты в код, документацию и вывод.
- Gradle передаёт свойства с префиксом `rfr.` в JVM тестов. Сохраняй этот механизм.
- Не запускай `localenv.sh` автоматически: он может остановить и удалить чужие Docker-контейнеры.

## Сценарии и изоляция

- Один тест проверяет одно поведение. Соблюдай глобальные требования к именам, утверждениям, данным и отсутствию общего изменяемого состояния; не копируй нарушения из существующих тестов.
- Для UI-тестов используй `@UsePlaywright` и параметр `Page`. Расширение управляет Playwright, браузером и отдельным контекстом каждого теста. Не создавай параллельный механизм управления браузером без согласования.
- Локаторы, клики, ввод, переходы и проверки интерфейса размещай в PO и компонентах. В тесте оставляй данные и последовательность бизнес-действий.
- Проверяй вход именно под подготовленным пользователем. Сохранённая сессия auth может пропустить форму входа и открыть чужой аккаунт.
- Используй уникальные данные для каждого теста и существующую генерацию данных. Не полагайся на порядок выполнения или заранее созданных общих пользователей.
- Не добавляй общие поля, `setUp`, `tearDown` и общие константы тестов вопреки глобальным правилам.
- В `junit-platform.properties` параллельный запуск сейчас отключён, хотя параметры конкурентного выполнения заданы. Не включай его в рамках несвязанной задачи; учитывай изоляцию данных и ограничения потоков Playwright при изменении конфигурации.
- Не маскируй стабильные ошибки повторными запусками. Повторы допустимы только для обоснованно нестабильных блоков по глобальным правилам.

## Подготовка данных и доступ к БД

- Для готового пользователя используй параметр `@User TestUser` из `junit.annotation.User` и `data.TestUser`. `UserExtension` создаёт отдельную `UserFixture` для параметра и сохраняет её в Store текущего теста.
- Различай `UserFixture.user()` и `create()`: первый предоставляет данные без записи пользователя, второй создаёт пользователя в auth. Профиль API создаёт приложение при первом обращении.
- Для регистрации через UI используй `UserFixture` в `try-with-resources`, чтобы fixture владела данными созданного аккаунта. Не добавляй дублирующую очистку в тестовые методы или общие lifecycle-методы.
- Сохраняй существующее освобождение ресурсов fixture при завершении контекста JUnit, включая падение теста. Очистка касается только данных конкретного тестового пользователя.
- При изменении очистки сохраняй попытку очистить auth даже после ошибки API. Не скрывай ошибки; сохраняй дополнительные исключения как suppressed. Между auth и API нет общей транзакции.
- Используй существующие `Databases`, `Jdbc`, `AuthUserRepository` и `ApiUserRepository`. SQL размещай в ресурсах, значения передавай именованными параметрами, а не конкатенацией строк.
- Транзакции выполняй через существующую инфраструктуру для соответствующей БД. Не переноси SQL и настройку подключений в PO или UI-сценарии.
- Не меняй схему БД из тестов. Изменения схемы оформляются миграциями соответствующего серверного модуля.

## Page Object и компоненты

- Следуй `rfr-page-objects`: страницы и компоненты — `public final`, взаимодействие переиспользуется через композицию. Не создавай `BasePage` и наследование реализации.
- Конструктор страницы принимает `Page page` и только присваивает поля, инициализирует локаторы и составные компоненты. Для компонента допустим корневой `Locator`. В конструкторах запрещены навигация, действия, проверки, ожидания и настройка страницы.
- Поля взаимодействия объявляй `private final`. Компоненты ограничивают поиск своей областью и не получают URL, если не являются страницами.
- Скилл предписывает страницам `public static String URL` на основе `TestConfig` и пути. Это конфликтует с глобальными ограничениями публичного состояния и неизменяемости: не считай скилл разрешением на исключение. Если задача требует изменить такое объявление или добавить новое, согласуй противоречие с пользователем до реализации.
- Аналогично соблюдай глобальное требование объявлять публичные методы сначала в интерфейсе и ограничение числа атрибутов. При препятствии в существующей архитектуре остановись и согласуй решение; не создавай обход или несвязанный рефакторинг.
- Один метод выполняет одно бизнес-действие. Связанные поля заполняй вместе, например `fillRegistrationForm(...)`, `fillLoginForm(...)`, `fillProfileForm(...)`.
- Заполнение и отправку формы разделяй: `fillRegistrationForm(...)` и `submitRegistration()`. Избегай общих имён `fillForm()` и `submit()`.
- Действия не содержат утверждений; возвращают текущую страницу или PO назначения. Методы получения состояния не содержат скрытых действий.
- Методы `should...` содержат только проверки и могут возвращать `this`. Не добавляй в них клики, ввод, переходы или обновление страницы.
- Не создавай `checkPageLoaded` и аналоги. Проверяй конкретное ожидаемое состояние средствами `PlaywrightAssertions.assertThat(...)` с автоматическим ожиданием.
- Для UI более конкретное требование скилла — проверки Playwright. Не заменяй их Hamcrest-проверками мгновенно прочитанного состояния. Глобальные ограничения количества утверждений и положения проверки при этом сохраняются.
- Не используй `Thread.sleep`, `waitForTimeout`, числовые таймауты и настройки ожиданий в миллисекундах.
- Если последующий шаг зависит от завершения асинхронного сохранения, синхронизируй действие через `page.waitForResponse(..., save::click)`. Для GraphQL различай запросы по `operationName`, а не только `/graphql`. Получение ответа не заменяет проверку результата сохранения.

## Локаторы и браузерная проверка

- Предпочитай роли, доступные имена, подписи и уникальные подсказки. Для неоднозначных имён задавай точное совпадение и область компонента; не подменяй её вызовом `first()`.
- Ссылку профиля в шапке ищи внутри `banner`: одноимённая ссылка может присутствовать в меню.
- Для MUI Select используй `COMBOBOX` с доступным именем поля, например `Location`. Страну выбирай через `OPTION` с `setHas(...)` по вложенному `IMG` с точным именем страны.
- Варианты MUI могут находиться в портале вне формы: ищи их от `page`. Не полагайся на имя варианта вида `France France`, объединяющее текст и alt флага.
- Проверяй локаторы через Playwright MCP на работающем приложении, когда инструмент доступен. Если приложение недоступно, изучи исходную разметку и явно укажи, что браузерная проверка не выполнена.
- Ручное прохождение сценария через MCP не является запуском автоматизированных тестов и по скиллу не требует согласования запуска тестов. В отчёте разделяй эти результаты.

## Allure и секреты

- Каждый публичный метод PO, выполняющий действие или проверку, отмечай `@Step` с понятным русским описанием. Конструкторы не являются шагами.
- Фиксируй входные параметры через параметры шагов Allure. Безопасные значения можно включать в название шага.
- Пароли и токены маскируй, например через `@Param(mode = Parameter.Mode.MASKED)`. Не вставляй секреты в названия шагов, обычные журналы и сообщения ошибок.
- Маскирование в отчёте не удаляет секреты из исходных результатов Allure. Не публикуй такие результаты без проверки их содержимого.
- Сохраняй скрытие пароля в `TestUser.toString()`. Не добавляй библиотеку логирования ради дублирования параметров Allure.

## Проверка поведения приложения

- Проверяй GraphQL `errors`: HTTP 200 сам по себе не подтверждает успех. Учитывай `NOT_FOUND`, `BAD_REQUEST` и `INTERNAL_ERROR`; внутренние подробности не должны попадать в пользовательский ответ.
- Сверяй операции с `rfr-api/src/main/resources/graphql/query.graphqls` и фактическими обработчиками. Часть операций фотографий и ленты возвращает статические данные из `resources/mock`.
- Успешный ответ заглушки не доказывает изменение БД. Для сохранения проверяй результат после повторного чтения или перезагрузки, когда операция реализована.
- Не подменяй отсутствующую серверную функциональность обходом в тесте. Если причина находится в приложении, подготовь описание проблемы и согласуй дальнейшую работу; issue создавай только после одобрения.
- Учитывай доступ к чужим объектам и отрицательные сценарии. Для API нужен access token с подходящей audience и правами; `id_token` для этого не подходит.

## Изменения и проверки

- Соблюдай глобальные требования к TDD. Перед любым запуском тестов назови конкретные классы или методы и дождись разрешения, если его ещё нет в текущем диалоге.
- Примеры команд ниже не являются разрешением на выполнение. Запускай их из корня проекта в PowerShell:

```powershell
.\gradlew.bat :rfr-e2e:compileTestJava
.\gradlew.bat :rfr-e2e:test --tests io.student.rangiffler.test.RegistrationTest
.\gradlew.bat :rfr-e2e:test --tests io.student.rangiffler.test.LoginTest
.\gradlew.bat :rfr-e2e:test --tests io.student.rangiffler.test.JdbcTest
```

- `compileTestJava` проверяет компиляцию, но не выполняет сценарии и не доказывает доступность приложения или корректность локаторов. Для Bash используй `./gradlew`.
- Для исправления ошибки сначала воспроизведи её согласованным тестом, затем исправь причину и покажи результат того же теста. Для изменения только документации сборка и тесты обычно не нужны.
- Форматируй изменяемый код штатным форматтером IntelliJ IDEA с настройками проекта. Не включай массовое форматирование и несвязанные исправления.
- При изменении PO обновляй затронутые вызовы и проверяй композицию, конструкторы, локаторы, разделение действий и утверждений, шаги и параметры Allure.
- HTML-отчёт тестов находится в `rfr-e2e/build/reports/tests/test/index.html`. Не добавляй в коммиты `build`, отчёты, результаты Allure, настройки IDE и локальные учётные данные.
- Не меняй правила исключения `AGENTS.md` и `docs/` без запроса пользователя. Не создавай коммиты и не отправляй изменения без предусмотренного глобальными правилами разрешения.
- В итоговом ответе укажи изменения, выполненные проверки и то, что не удалось проверить. Не представляй компиляцию или проверку через MCP как успешный запуск автотестов.
