# Правила модуля rfr-auth

## Область действия

- Инструкции действуют для всего `rfr-auth` и дополняют глобальные правила и корневой `AGENTS.md`. Требования к Git, файлам и согласованию тестов сохраняются.
- Пиши ответы и документацию на русском языке, используй UTF-8. Сохраняй имена протоколов, API и существующий текст интерфейса, если задача не требует его изменения.
- Перед изменениями прочитай корневой `README.md`, `rfr-auth/README.md`, затронутый код и конфигурацию. Описание в README не заменяет проверку реализации, особенно для security и срока жизни токенов.

## Назначение и структура

Модуль регистрирует пользователей, показывает страницы входа и выдаёт токены по OAuth 2.0 / OpenID Connect. Используются Spring Boot, Spring Security, Authorization Server, JPA, Flyway и Thymeleaf. Версии определяются файлами сборки.

Исходники находятся в `src/main/java/io/student/rangiffler`.

| Пакет или каталог | Назначение |
| --- | --- |
| `controller` | Вход, регистрация и страницы ошибок |
| `service/api`, `service/impl` | Регистрация и загрузка учётной записи |
| `data`, `data/repository` | Пользователи, права и доступ к БД |
| `model`, `validation` | Форма регистрации и ограничения полей |
| `config`, `service/cors` | Security, токены, отзыв, тема и CORS |
| `service/OidcClearCookiesLogoutHandler` | Очистка cookies при OIDC logout |
| `src/main/resources/templates` | Шаблоны Thymeleaf |
| `src/main/resources/static` | Стили, изображения и шрифты |
| `src/main/resources/db/migration/rangiffler-auth` | Миграции БД auth |

- Сохраняй разделение контроллеров, сервисов и репозиториев. Не переноси регистрацию в security-фильтры или шаблоны.
- Соблюдай глобальные правила объектов с необходимыми исключениями для Spring и JPA. Не используй существующие отступления как основание для новых.

## OAuth и безопасность

- Сохраняй порядок и области двух `SecurityFilterChain`: протокольные endpoint Authorization Server и обычные страницы приложения.
- Клиент SPA публичный, использует Authorization Code с PKCE. Не добавляй секрет во frontend и не отключай PKCE ради исправления входа.
- Настройки клиента, redirect URI, post-logout redirect URI, issuer и CORS должны соответствовать клиенту и API. Читай значения из `application.yaml` и существующих свойств, не дублируй адреса в Java и шаблонах.
- Сохраняй CSRF-защиту форм и существующие правила протокольных endpoint. Не отключай защиту целиком ради отдельного запроса.
- `AccessTokenCustomizer` добавляет audience API и пользовательские `authorities` только в access token; служебные `FACTOR_*` не должны становиться правами приложения.
- Access token предназначен для `rfr-api`; `id_token` — для клиента и `id_token_hint` при logout. Не подменяй один другим.
- Сроки жизни токенов и сессии проверяй по конфигурации и реализации. В README есть расходящиеся значения; не закрепляй произвольное значение в новом коде и правилах.
- Ключ RSA сейчас создаётся при старте, поэтому перезапуск меняет ключ подписи. Не добавляй постоянные ключи в репозиторий; изменение хранения ключей требует отдельного решения.
- Учитывай существующий механизм отзыва для публичного клиента через `client_id`. Не расширяй его на другие операции без проверки требований протокола.
- Отзыв авторизации не гарантирует немедленный отказ API: API проверяет самодостаточный JWT локально. Не обещай такое поведение без изменения механизма проверки.
- При logout сохраняй завершение серверной сессии, очистку `JSESSIONID` и `XSRF-TOKEN` и согласованный переход на клиент.
- Не выводи пароли, токены, cookies и ключи в журналы, ответы и отчёты.

## Регистрация и данные

- Сохраняй серверную валидацию `RegistrationForm`, включая совпадение паролей и запрет недопустимых пробелов. Клиентская валидация её не заменяет.
- Пароль кодируй существующим `PasswordEncoder`; не сохраняй открытый пароль и не подменяй совместимый формат произвольным хешем.
- Создание пользователя и его прав должно оставаться атомарным. Используй права из существующей модели, согласованные с API.
- Уникальность username должна обеспечиваться БД. Сохраняй обработку конфликта, включая одновременную регистрацию одного имени.
- Сохраняй контракт регистрации: успешный результат — HTTP 201, ошибка валидации или занятое имя — HTTP 400 с ошибками формы.
- Миграции добавляй в каталог auth; не переписывай применённые миграции. Не создавай профиль API прямой записью в чужую БД из auth.

## Шаблоны и тема

- Используй существующие шаблоны Thymeleaf и статические ресурсы. Не добавляй React, Material UI или новую библиотеку компонентов в серверные страницы.
- Сохраняй привязку полей, отображение ошибок и экранирование пользовательского ввода. Не выводи непроверенные данные как HTML.
- Страницы login и register участвуют в OAuth-сценарии: проверяй сохранение контекста авторизации и корректность переходов. Прямое открытие `/login` не эквивалентно началу OAuth-входа.
- Сохраняй светлую, тёмную и системную темы. `ThemeCookieFilter` обрабатывает `theme=light|dark` и cookie `rangiffler-theme`; проверяй фактическую разметку и стили перед изменением.
- Учитывай доступные имена полей и элементов: они используются также UI-тестами. При изменении контракта интерфейса согласованно обновляй затронутые PO по правилам `rfr-e2e`.

## Запуск и проверки

- Конфигурация — `src/main/resources/application.yaml`, локальный адрес — `http://localhost:9001`. Нужна БД auth с миграциями; для полного входа нужны также клиент и API.
- Команды из корня проекта в PowerShell:

```powershell
.\gradlew.bat :rfr-auth:compileJava
.\gradlew.bat :rfr-auth:bootRun
```

- Для Bash используй `./gradlew`. Не запускай `localenv.sh` автоматически.
- Перед запуском тестов согласуй конкретные тесты. Для исправлений следуй глобальному TDD; отдельно учитывай негативные сценарии регистрации и нарушения OAuth-контракта.
- Компиляция не проверяет security chains, обмен токенов, шаблоны и запросы JPA при старте с БД. Указывай, какие из этих проверок фактически выполнены.
- Форматируй код штатным форматтером IntelliJ IDEA. Для изменения только документации сборка и тесты обычно не нужны.
