# Тестовые данные rfr-e2e — v1

Перед изменениями прочитай текущие UserRequest, UserFixture, TestUser и затронутые объекты data/db. Пути Java-кода отсчитываются от rfr-e2e/src/test/java/io/student/rangiffler/.

**Уникальность данных.** Создавай отдельные данные для каждого независимого параметра @User и вызова теста: UUID и логины через существующий RandomDataUtils, без общих изменяемых пользователей и фиксированных логинов. Для негативного сценария нарушай только проверяемое ограничение; пароли не включай в логи и названия шагов.

**Владелец — дерево декораторов.** UserExtension сохраняет корень UserFixture из UserRequest.fixture() в Store до create(), и JUnit закрывает его как AutoCloseable; при ручном использовании применяй try-with-resources. Каждый декоратор владеет origin и дополнительными фикстурами, включая частично созданных участников; освобождай их через TearDown перед origin, продолжая очистку после ошибок и сохраняя suppressed-исключения.

**Новое предусловие — новый декоратор.** Подключай декоратор в UserRequest.fixture(), как UserWithFriendsFixture, UserWithIncomeInvitations и UserWithOutcomeInvitationsFixture. Не добавляй ветки подготовки в UserExtension и флаги в SingleUserFixture; связанных пользователей передавай через соответствующие списки TestUser.

**SQL — в объектах строк data/db.** Подготовку и очистку выполняют AuthAccount, Authorities, Profile и Friendships, привязанные к TestUser; fixture и тест вызывают их методы, не пишут SQL и не управляют JDBC. Тексты запросов храни в rfr-e2e/src/test/resources/sql, значения передавай именованными параметрами; удаляй только принадлежащие тесту данные адресно по username, без широких DELETE и TRUNCATE.

**Профиль API создаётся явно.** SingleUserFixture.create() сначала создаёт AuthAccount с правами, затем Profile с тем же UUID; учётная запись auth сама по себе не гарантирует наличие профиля API. Не полагайся на первый вход или побочный эффект запроса; при ошибке любого этапа уже созданные данные должны оставаться под управлением очистки.

**Пул — только когда создать нельзя.** По умолчанию создавай пользователей через фикстуры; заранее заведённый пул допустим лишь при конкретном ограничении, исключающем создание нужных данных. Для пула явно определи исключительное владение пользователем на время теста и восстановление изменённого состояния, не позволяя тестам одновременно менять одну запись.

Используй минимальные предусловия: одна нужная связь вместо нескольких лишних пользователей. Проверки запускай только с разрешения по правилам проекта; отдельно сообщай, что проверено запуском и что установлено по коду.
