# Создание Page Object

Пиши инструкции, описания шагов и отчёты на русском языке. Сохраняй имена Java API и фактический текст элементов интерфейса.

## Структура и переиспользование

- Объявляй классы страниц и компонентов `public final`.
- Конструктор PO принимает `Page page` и выполняет только присвоение `this.page = page` и инициализацию остальных `private final` полей PO: локаторов и составных компонентов. Не выполняй в конструкторе навигацию, действия с интерфейсом, проверки, ожидания или настройку страницы.
- Для переиспользуемых компонентов допускается передача корневого `Locator`; их конструкторы также выполняют только присвоения и инициализацию `private final` полей.
- Переиспользуй функциональность через композицию: выделяй шапку, меню, формы и другие повторяющиеся части в отдельные компоненты. Не создавай `BasePage` и не наследуй страницы друг от друга.
- Компоненты ограничивают локаторы своей областью. Не добавляй URL к компонентам, не являющимся отдельными страницами.
- Для каждой страницы объявляй `public static String URL`. Собирай адрес из `TestConfig` и пути страницы, например `public static String URL = TestConfig.FRONT_URL + "/profile";`. Не дублируй адреса окружений в PO.

## Методы действий

- Один метод описывает одно бизнес-действие. Объединяй заполнение связанных полей формы в один метод, а не заставляй тест отдельно заполнять каждое поле.
- Имя метода должно явно описывать конкретную форму или бизнес-действие: например, `fillRegistrationForm(...)`, `fillLoginForm(...)`, `updateProfile(...)`, `submitRegistration()` или `signIn()`. `fillForm(...)` и `submit()` — условные примеры структуры, а не рекомендуемые имена; не используй такие общие имена в реальных PO.
- Отделяй заполнение формы от отправки: например, `fillRegistrationForm(...)` заполняет поля, а `submitRegistration()` отправляет регистрацию. Оба метода могут вызываться последовательно в тесте.
- Действия не содержат утверждений. Возвращай текущую страницу для продолжения работы или соответствующий PO при переходе на другую страницу.
- Не добавляй скрытые переходы, клики или заполнение полей в методы получения состояния.

## Методы проверок

- Не создавай методы `checkPageLoaded` и их аналоги для общей проверки или ожидания загрузки страницы. Используй web-first assertions Playwright для конкретного ожидаемого состояния интерфейса непосредственно в соответствующих методах проверок; отдельная предварительная проверка загрузки не нужна.
- Методы `should...` содержат только проверки; допустим возврат `this` для цепочки вызовов.
- Не выполняй внутри проверок навигацию, клики, заполнение, обновление страницы и другие действия, меняющие состояние приложения.
- По умолчанию используй условия Playwright через `PlaywrightAssertions.assertThat(...)`: `isVisible()`, `hasText()`, `hasValue()`, `hasURL()` и другие подходящие условия. Другой механизм используй только по прямому указанию пользователя.
- Используй автоматические ожидания действий и проверок Playwright. Не добавляй `Thread.sleep`, `waitForTimeout`, числовые таймауты и настройки ожиданий в миллисекундах.

## Allure и параметры

- Каждый публичный метод PO, выполняющий действие или проверку, обязательно помечай `@Step` с понятным описанием на русском языке. Конструкторы не являются шагами.
- Логируй входные параметры через параметры шагов Allure; значимые безопасные значения можно также включать в название шага, например `@Step("Проверить логин: {username}")`.
- Пароли, токены и другие секреты маскируй в параметрах отчёта, например `@Param(mode = Parameter.Mode.MASKED)`. Не вставляй их в текст `@Step` и не выводи обычным логированием. Учитывай, что маскирование отчёта не удаляет секрет из исходных результатов Allure.
- Не добавляй отдельную библиотеку логирования, если параметры уже фиксируются имеющимся Allure.

## Работа с интерфейсом

- Перед написанием PO изучи существующие классы, `TestConfig` и зависимости проекта.
- Прохождение сценария через Playwright MCP — это браузерная проверка, а не запуск автоматизированного теста проекта. Требование согласовывать запуск тестов не распространяется на прохождение сценариев через MCP. В отчёте отдельно указывай результат проверки через MCP и результат запуска автоматизированных тестов.
- Проверяй локаторы на работающем интерфейсе через PW MCP, когда он доступен. Предпочитай роли, доступные имена, подписи и уникальные подсказки. Если приложение недоступно, исследуй разметку и явно сообщи, что браузерная проверка не выполнена.
- Если одинаковые элементы встречаются несколько раз, ограничивай область поиска компонентом, например `banner` для ссылки профиля в шапке. Не используй `first()` вместо определения нужной области.
- Держи локаторы и детали браузерного взаимодействия в PO и компонентах; данные и конфигурацию бери из соответствующих классов тестового проекта.

## Проверка результата

При создании или изменении PO проверь, что классы `final`, URL вынесены в `public static String URL`, повторяющаяся функциональность использует композицию, шаги и параметры отражены в Allure, заполнение связанных полей объединено в один метод с конкретным бизнес-именем, а проверки не содержат действий. Обнови затрагиваемые вызовы в тестах. Выполняй подходящие проверки с учётом разрешений текущего диалога и сообщай фактический результат. Создание этого скилла само по себе не требует изменения существующих PO.
